# Architecture Decision Record

Living record of architectural decisions. Distinct from `CHANGELOG.md` (chronological log of *changes*) — this is a log of *decisions*: what was decided, why, what alternatives were considered and rejected, and what it affects. ## Pre-implementation decisions (from `docs/technical_architecture.md` and `docs/approach.md`)

### D1 — Two-layer verification: deterministic symbolic/rule-based check before any LLM involvement
**Decision:** Every step submission is checked by sympy + a per-topic rule engine before the LLM is ever invoked. The verifier is a hard pipeline gate called directly by application code — never a tool the LLM decides when to invoke.
**Why:** A pure-LLM checker can mis-grade a correct step as wrong or miss a real error; for a young learner with no way to sanity-check the tutor, an unreliable correction is worse than none. Reinforced by Davis & Aaronson 2023 (E4) — GPT-4 + WolframAlpha + Code Interpreter still failed largely due to "interface failures" (the LLM mis-formulating its own tool query), showing that even giving an LLM a correctness tool doesn't work if the LLM controls when/how to call it. Alternative considered and rejected: let the LLM call a `check_step()` function at its own discretion — rejected because it reintroduces the exact failure mode the two-layer split exists to eliminate.
**Affects:** Verification Service design (§3), pipeline shape (§1): verify → classify → retrieve → converse → re-verify → log.

### D2 — Bias toward false negatives over false positives in the verifier
**Decision:** When verifier confidence is low, don't interrupt, rather than risk wrongly telling a child they're wrong.
**Why:** Wrongly accusing a correct step of being wrong is more damaging to trust than occasionally missing a real error, especially for a 10-year-old who can't push back on the tutor.
**Affects:** Verifier confidence thresholding, must be explicit and tested, not emergent.

### D3 — Error classification is closed-set, not open-ended
**Decision:** Retrieve candidate misconceptions for the current `(topic, step_type)` from the misconception bank before calling the LLM; the LLM picks among them or says "none of these." Never let it freely diagnose.
**Why:** Otero, Druga & Lan 2025 (B7) — GPT-4-turbo misconception accuracy jumped from 52.96% (unconstrained) to 73.82–83.91% (topic-constrained). Jin et al. 2024 (B8) — all 16 tested LLMs scored F1<0.5 diagnosing *why* a student erred, with strong overconfidence specifically on wrong diagnoses (the failure mode is "confidently wrong," not "appropriately unsure").
**Affects:** Error Classification service (§4), Misconception Bank retrieval (§5) — retrieval now runs twice per error (once to constrain classification, once to ground dialogue generation).
**Supersedes:** original design where "LLM fallback classifies novel errors directly into the taxonomy" (see `docs/technical_architecture.md` §0 row 1).

### D4 — Buggy-rule library first, LLM fallback second for error classification
**Decision:** A pattern-matchable library of known buggy rules (Brown & Burton / VanLehn tradition) is checked first; the LLM only classifies when no signature matches.
**Why:** A large fraction of primary arithmetic errors are enumerable, systematic procedural bugs, not random noise (B1–B3). Cheap, deterministic, explainable, and a genuine bridge between classic symbolic ITS research and modern LLM tutoring for the paper's framing.
**Affects:** Error Classification service (§4). Directly motivates the phase-0 topic choice (subtraction-with-borrowing has the deepest buggy-rule literature of any NCERT Class 5 topic).

### D5 — Novel/LLM-classified errors are never auto-promoted into the trusted taxonomy
**Decision:** LLM classifications always carry a lower-confidence flag and route to a semi-automated review queue — similar novel errors clustered before a human reviewer looks, per Feldman et al. 2018 (B4)'s CHI 2018 approach — rather than one-by-one triage or silent auto-promotion.
**Why:** LLM classification overconfidence (D3's Jin et al. citation) means an unsupervised LLM diagnosis can't be trusted at the same tier as a buggy-rule-signature match. Clustering first turns "triage 12 near-duplicate items" into "confirm this cluster is a new bug, once."
**Affects:** Error Classification service (§4) review-queue design; this is the system's data flywheel — confirmed novel bugs get promoted into the buggy-rule library and misconception bank.

### D6 — "Examinee vs. diagnostician" role-framing fix in the classification prompt
**Decision:** Classification prompts must explicitly instruct the LLM that it is not solving the problem — the correct answer is given — its only job is to explain the reasoning path that would produce the *student's* incorrect answer.
**Why:** Song et al. 2026 (B10) named a reproducible failure mode: LLMs asked to explain a wrong answer default to an "examinee" mindset (quietly re-solving) instead of a "diagnostician" mindset (reasoning about why *this* answer is wrong given the student's actual approach).
**Affects:** Error Classification prompt design (§4); becomes an explicit eval case (§9) — does the stated reasoning path match the student's apparent approach, or does it just re-derive the correct answer and note a discrepancy.

### D7 — Every dialogue turn is decide-then-generate, not error-to-message directly
**Decision:** Each turn is two structured calls (or two phases of one call): call 1 outputs `{error_type, remediation_strategy, instructional_intent}` grounded in the verifier's output and retrieved misconception entry; call 2 generates the child-facing `message` conditioned on that decision object.
**Why:** Wang, Zhang, Robinson, Loeb & Demszky 2024 ("Bridge," NAACL, C5) — GPT-4 conditioned on an explicit expert decision framework was preferred 76% more than unconditioned generation; *randomly assigned* decisions (going through the motions without being the right decision) cut quality by 97% vs. expert-informed decisions. The decision content has to actually be right — which is why it's fed by the retrieved, topic-constrained misconception match (D3), not invented fresh each turn.
**Affects:** Dialogue Orchestrator (§6) turn structure; makes strategy-selection independently loggable/evaluable, separate from message wording (§9).
**Supersedes:** original design where the orchestrator "generates a Socratic message directly from (error, misconception context)" (`docs/technical_architecture.md` §0 row 2).

### D8 — Deterministic, per-turn answer-leakage filter
**Decision:** Before any generated message reaches the child, string/value-match it against the known correct step/final answer (and close paraphrases/numeric matches) from the problem schema; reject-and-regenerate on match, with an explicit "don't state the answer" instruction appended to the regeneration prompt.
**Why:** SafeTutors (Hazra et al. 2026, E8) — pedagogical-harm rate (mostly premature answer disclosure) rose from 17.7% at turn 1 to 77.8% by later turns across every tested model; prompting alone is not sufficient once a dialogue runs several turns. Because the system already has ground-truth from the problem schema, this is cheap to check deterministically rather than via a generic moderation pass.
**Affects:** Dialogue Orchestrator (§6) output pipeline; interacts with streaming (only stream after a message passes both gates, never speculatively). Lee et al. 2026's "LeakShield" prompting technique (C10) adopted as first line of defense before the filter has to trigger a (turn-budget-costing) regeneration.
**Supersedes:** original design of "turn-budget cap + one output-safety pass" (`docs/technical_architecture.md` §0 row 3).

### D9 — Measurable readability gate (Flesch-Kincaid or similar), not just a prompt instruction
**Decision:** Run a readability check on every generated message against a target ceiling appropriate for a Class 5 reader; regenerate with an explicit simplification instruction if it fails.
**Why:** Parra, Corica & Godoy 2026 (C13) — LLM tutor responses require a *higher* reading level than human tutors' by default, across every tested model; the model doesn't self-correct without being forced to. Jiao et al. 2025 (E10) — children over-trust AI responses even when wrong, partly *because* of confident/anthropomorphized phrasing, so an over-complex explanation is also more likely to be blindly accepted.
**Affects:** Dialogue Orchestrator (§6) output pipeline, same regenerate-on-fail pattern as D8. Needs its own regression test set (known-over-complex drafts that must be caught), tracked as filter precision/recall (§9).
**Supersedes:** original design of "'age-appropriate tone' as a prompt instruction" (`docs/technical_architecture.md` §0 row 4).

### D10 — Intervention timing is a configurable orchestrator policy, not a hardcoded default
**Decision:** The orchestrator exposes intervention timing as a policy parameter consulted per step — "interrupt on first error" / "interrupt after Nth repeated error on the same step" / "wait for problem completion" — rather than one hardcoded behavior with alternates special-cased for the study.
**Why:** The feedback-timing literature is genuinely unsettled, not a case of "immediate is obviously right with delayed only as a study comparison arm." Kandemir et al. 2026 (D4 in lit survey) found no significant average timing effect in computer-assisted learning specifically (g=0.03); Metcalfe, Kornell & Finn 2009 (D7 in lit survey) found delayed feedback beat immediate for children on a (declarative) learning task; Young, Bevan & Sanders 2024 (D10 in lit survey) found the productive-struggle literature hasn't resolved when outside intervention helps vs. short-circuits useful struggle.
**Affects:** Dialogue Orchestrator (§6) state machine; directly simplifies running the three-condition RCT later, since conditions become policy configs rather than special-cased code paths. Experiment Assignment service (§8) persists the assigned condition per student/session from day one.
**Supersedes:** original design where "immediate interruption" was implicitly the hardcoded default (`docs/technical_architecture.md` §0 row 7).

### D11 — Step graph (DAG), not a linear step list
**Decision:** Problems are authored with a DAG of acceptable intermediate states, not a single prescribed sequence. The verifier checks the student's step against every reachable node, not just the immediate expected successor. A match against a non-adjacent-but-valid node is accepted but flagged for review, not silently accepted or rejected.
**Why:** Class 5 problems often have more than one legitimate solution path. Shih et al. 2023 (A8/D9 in lit survey)'s own deployed fractions ITS explicitly couldn't capture "all possible patterns of learners' responses" because it matched against a fixed pattern library instead of a full graph — real evidence, not a theoretical concern, that this failure mode bites in practice.
**Affects:** Problem/step-schema representation (§2), Verification Service (§3).

### D12 — Structured, math-aware step input only, never free-text math parsing
**Decision:** Students submit steps through a math-aware input widget (MathQuill-style or per-step-type structured fields) that emits an unambiguous structured value (small JSON AST or constrained LaTeX subset) — never a raw string to be parsed.
**Why:** Sidesteps an entire class of notation-ambiguity bugs (implicit multiplication, fraction-bar parsing, sign placement) that would otherwise consume a large fraction of engineering time for little research value.
**Affects:** Frontend step-input widget (§2, §11 build sequence step 5), Verification Service input contract (§3).
**Superseded (2026-08-15) for the `fractions_addition` topic only, by explicit founder request — see D37.** D12 remains the default for every other topic; nothing here reopens it generally.

### D13 — Typing friction is a documented UX failure mode for this age group
**Decision:** Minimize keystrokes per step at the widget level (numeric keypad, drag-to-place-digit, tap-to-select from a small candidate set wherever the step type allows); track time-to-submit-a-step as a pilot UX metric.
**Why:** Shih et al. 2023 (A8)'s real 6th-grade deployment explicitly reported keyboard/mouse input as "time-consuming and inconvenient," causing impatience.
**Affects:** Frontend step-input widget design (§2); pilot instrumentation (§9, §11 build sequence step 7).

### D14 — Turn budget with graceful fallback
**Decision:** Cap dialogue turns per step (3–4). After the cap, show a fully worked example and let the student proceed, logging the step as "escalated."
**Why:** Open-ended multi-turn dialogue risks a frustration loop if the child still doesn't get it after several tries (`docs/approach.md` §7). Escalation rate is itself a useful research signal — how often dialogue alone fails to get the student there.
**Affects:** Dialogue Orchestrator (§6) state machine.

### D15 — Re-verification on every retry, never LLM self-assessment
**Decision:** When a student resubmits a step mid-dialogue, the resubmission goes back through the deterministic Verification Service (D1), never through the LLM's judgment of whether the student "seems to get it now."
**Why:** Keeps multi-turn dialogue from drifting away from the grounding that made single-turn correction reliable in the first place; the two-layer verification idea otherwise only really protects the first correction.
**Affects:** Dialogue Orchestrator (§6) `AwaitingRetry` state transition.

### D16 — Attention-based (SAKT-style), not recurrence-based (DKT/LSTM), if/when a learned knowledge-tracing model is justified
**Decision:** v1 uses a simple, explainable mastery score (basic BKT update or decaying success-rate counter), not a deep KT model. *If* v2 data volume justifies a learned model, prefer an attention-based architecture (SAKT) over LSTM-based DKT.
**Why:** RNN-based KT models need long interaction histories; a single Class-5 tutoring session is far shorter/sparser than DKT's benchmark datasets (thousands of interactions/student). Pandey & Karypis 2019 (A3 sub-bullet) reported SAKT ~4.4% average AUC improvement over DKT-family baselines specifically on sparse-history data.
**Affects:** Student Model (§7) — v1 scope explicitly excludes deep KT; only changes what "v2" should reach for.
**Supersedes:** original doc's generic "DKT/LSTM" naming as the eventual upgrade path (`docs/technical_architecture.md` §7 revision note).

### D17 — LLM provider: Groq, not Anthropic/OpenAI
**Decision:** LLM access goes through the Groq API (fast open-weight model inference), behind a provider-agnostic wrapper (thin interface around "classify" / "decide" / "generate" calls) so switching models or providers is a config change, not a rewrite. Model selection must verify structured-output/tool-calling reliability before committing, not assume it. No key available yet — phases 1–2 (schema, verifier, buggy-rule matching) build and test fully unblocked with no LLM calls; the LLM-calling interface is stubbed with realistic fake responses until a key is provided.
**Why:** Explicit project-level instruction (`CLAUDE.md`). This is a real deviation from most of the literature survey's evaluated models (GPT-4/Claude-class), so it's treated deliberately: because Groq-hosted open models may be weaker at exactly the diagnosis/error-localization tasks the survey already flags as unreliable even for frontier models (Jin et al. 2024, B8; Srivatsa et al. 2025, C12), this *strengthens* rather than loosens the case for the deterministic verifier and closed-set classification (D1, D3) — guardrails don't get relaxed to compensate for a smaller model.
**Affects:** LLM client design (§8), every LLM-touching service (§4, §6). All real Groq calls, once wired, are logged in full (prompt, response, latency, token cost).
**Supersedes:** `docs/technical_architecture.md` §8's line "LLM access: Claude via API, structured/tool-output mode..." — that line reflected an earlier planning-stage assumption and was never updated in the source doc. Superseded 2026-08-13, before any implementation, per explicit instruction in `CLAUDE.md`.

### D18 — DPDP Act 2023 / DPDP Rules 2025 compliance is a pre-pilot gate, not a paperwork footnote
**Decision:** Qualified legal guidance on DPDP compliance (verifiable parental consent, Rule 10 restrictions on behavioral tracking of children's data) is required before any real student's data is collected, even a small pilot. This has consent-flow implications for the product itself (e.g., a parental-consent gate before a child's account can generate logged data), not just paperwork to file separately.
**Why:** The system handles data from children under 18 in India; the per-student misconception/knowledge model (Student Model, §7) is exactly the kind of behavioral tracking the DPDP Rules target.
**Affects:** Pilot planning (§11 build sequence step 7), Student Model / Event Log design (§7, §8) — flagged to Arnav early per `CLAUDE.md`'s compliance note, not deferred.

## Project-scoping decisions (from `docs/approach.md` §7 and `CLAUDE.md`)

### D19 — Sequence topic coverage; don't build the full syllabus before shipping
**Decision:** Architect every interface (step schema, verifier interface, error taxonomy, dialogue engine, logging) topic-agnostic and ready for the full syllabus, but ship the first working slice against one topic, pilot it, then expand chapter by chapter.
**Why:** Symbolic verification effort is not uniform across topics (arithmetic is cheap, geometry/data-handling/patterns are each their own hard problem). For the research study specifically, coverage breadth actively hurts statistical power — narrower topic coverage with more repetitions per error type beats shallow coverage of everything. "Architecture is topic-agnostic, ships N of M chapters" is not in tension with "built for full Class 5 math" as a product claim.
**Affects:** Overall build sequence (`docs/technical_architecture.md` §11); directly produced the phase-0 topic audit (2026-08-13 entry, `CHANGELOG.md`).

### D20 — First-slice topic: NCERT Class 5 Chapter 1, multi-digit subtraction with borrowing
**Decision:** The first verifier/misconception-bank slice targets subtraction with borrowing on large numbers (NCERT Ch.1, "The Fish Tale"), confirmed by Arnav on 2026-08-13 after a chapter-by-chapter audit of all 14 NCERT Class 5 Math-Magic chapters.
**Why:** Of all 14 chapters, this one has by far the deepest misconception-literature grounding (Brown & Burton's DEBUGGY, VanLehn's repair theory — B1–B3) and one of the cleanest step-DAG decompositions. Runners-up considered: Ch.13 long division (richest step-DAG in the syllabus, but the survey's specific bug-tradition citations center on subtraction) and Ch.6 LCM/HCF (also clean, weaker literature grounding). Chapters ruled out for v1 step-verification: Shapes and Angles, How Many Squares?, Does it Look the Same?, Can You See the Pattern?, Mapping Your Way, Boxes and Sketches, Smart Charts — these are recognition/visual/interpretive tasks, not linear checkable procedures, matching the caveat already flagged in `docs/approach.md` §7.
**Affects:** Phase 1 (`docs/technical_architecture.md` §11 step 1) — step schema, verifier, and misconception bank all built first against this topic. See full audit table in `CHANGELOG.md`, 2026-08-13 09:15 entry.

### D24 — Buggy-rule matching is direct Python predicates, not a formula-string interpreter
**Decision:** `classification/rule_matcher.py` implements each of the four seeded buggy-rule signatures (B1-B4) as a dedicated, testable Python function operating on a `(correct_fields, student_fields)` pair — it does not `eval()` or otherwise interpret the seeded `buggy_rule_library.signature_matcher` JSON's `student_formula` string at runtime.
**Why:** Evaluating an arbitrary formula string is both a security liability (even against trusted seed data, it invites scope creep toward evaluating less-trusted input later) and harder to test/debug than a plain function. The seeded declarative JSON remains valuable as the reviewable, citable artifact (technical_architecture.md §4's "genuine bridge between classic symbolic ITS research and modern LLM tutoring") — this decision just means the JSON documents the pattern for humans while the Python function is the actual executable check, and the two are kept in sync by a cross-matrix test (`test_rule_matcher.py`) that verifies each matcher fires on its own seeded `example_pair` and *not* on any other bug's.
**Affects:** `classification/rule_matcher.py`. A genuinely general formula DSL is a fair v2 idea if the buggy-rule library grows large enough that hand-writing a Python predicate per bug stops scaling — not needed at 4 bugs / 1 topic.

### D25 — LLM client: three-method Protocol built now, logging centralized in a wrapper, Groq provider written but gated unusable without a verified model
**Decision:** `llm/client.py` defines the full `LLMClient` Protocol (`classify`/`decide`/`generate`) even though Phase 2 only calls `classify()` — `decide`/`generate` are stubbed to raise `NotImplementedError` in `GroqLLMProvider` until Phase 3. Every call, from any provider, is logged (prompt, response, latency, cost) by a single `LoggingLLMClient` wrapper rather than duplicated per-provider logging code. `build_llm_client()` raises immediately if `LLM_PROVIDER=groq` is set without both `GROQ_API_KEY` and `GROQ_MODEL` — there is no default model to silently fall back to.
**Why:** CLAUDE.md's explicit instruction to build the provider-agnostic interface up front, log every real call once wired, and never assume a Groq model's structured-output reliability without verifying it directly. Making the "no model configured" case a hard `RuntimeError` (not a silently-chosen default) is what actually enforces the "verify before use" instruction in code, not just in a comment.
**Affects:** `llm/client.py`, `llm/providers/mock.py` (default provider, fully tested, deterministic on purpose so tests don't need to tolerate randomness), `llm/providers/groq.py` (written to the shape of Groq's OpenAI-compatible JSON-mode chat-completions API, **not verified against a live API** — no key exists yet; smoke-tested only for constructibility, not for real structured-output behavior).
**Open task, not yet done:** once a Groq key is provided, directly test the chosen model's structured-output/tool-calling reliability before relying on it anywhere beyond local supervised testing, per CLAUDE.md.

### D26 — Classification orchestrator: rule match short-circuits before any DB/LLM access; closed-set validation happens in application code regardless of provider
**Decision:** `classification/classifier.py`'s `classify_error()` tries the buggy-rule matcher first; only if nothing matches does it retrieve misconception-bank candidates and call the LLM. The LLM's returned `misconception_id` is checked against the exact retrieved candidate-id set in application code — any id outside that set (or `None`) is routed to the novel-error review queue, never trusted as-is. LLM-sourced classifications always carry `confidence="low"`; only rule matches carry `confidence="high"`.
**Why:** Direct implementation of D3/D4/D5. Short-circuiting on a rule match before touching the DB or LLM keeps the common case (a known bug) cheap and fast, and keeps the rule-match path unit-testable without any DB/network dependency (`tests/unit/classification/test_classifier.py`) — only the LLM-fallback path needs integration-test coverage against a real Postgres.
**Affects:** `classification/classifier.py`, `db/repositories/misconception_repository.py` (retrieve-don't-dump — only `(topic, step_type)`-scoped candidates are ever loaded), `db/repositories/novel_error_repository.py`.

### D27 — Novel-error clustering: a stable structural-signature string, not ML
**Decision:** `classification/clustering.py`'s `cluster_signature(topic, step_type, discrepant_fields)` produces a deterministic key (sorted discrepant-field names + a short hash) used to group `novel_errors` rows. `cluster_pending_novel_errors()` assigns this signature to every unclustered row and is idempotent (already-clustered rows are untouched; re-running clusters nothing new).
**Why:** Feldman et al. 2018's clustering-before-human-review approach (D5) doesn't require anything more sophisticated at this scale — "same topic, same step type, same fields disagreed" is already a meaningful, cheap grouping that turns "review 12 near-duplicate novel errors" into "confirm this one cluster is a new bug." A real similarity-embedding approach is a reasonable v2 if/when the novel-error volume from a real pilot makes a plain structural key too coarse — not needed yet, and not build-time-blocking for Phase 2.
**Affects:** `classification/clustering.py`, `db/models/novel_error.py` (migration `0002_novel_errors.py`). Promoting a confirmed cluster into `buggy_rule_library`/`misconception_bank` is explicitly out of scope here — that's Phase 6 (real pilot), per the approved build plan.

### D28 — Dialogue state machine: only `AwaitingRetry` and a tracking-only `ErrorDetected` are ever persisted between calls
**Decision:** `dialogue/state.py`'s persisted `DialogueState` really only takes two meaningfully-different forms across calls: `AwaitingRetry` (an active dialogue mid-turn, with a real conversation and a nonzero `turn_count`) and a `ErrorDetected` tracking-only record (no conversation, `turn_count` stays 0) used purely to persist `consecutive_errors_on_this_step` across calls where the timing policy decided *not* to intervene yet. `Explaining` is a transient, in-request-only step of producing a turn, never itself written to Redis. A correct submission always deletes whatever's there, whether that's a real dialogue (→ `resolved`) or just tracking (→ plain `no_action`).
**Why:** A real bug surfaced during testing: the first implementation didn't persist anything at all when the timing policy said "don't intervene yet," which meant `AFTER_NTH_REPEAT` could never actually reach its threshold — every subsequent call saw an empty state and reset the count back to 1. `test_after_nth_repeat_policy_waits_for_the_second_wrong_attempt` (`tests/unit/dialogue/test_orchestrator.py`) caught this on first run. The fix persists a minimal tracking record even in the no-intervention path, keyed by the same `(session_id, problem_id)` Redis key as the real dialogue state.
**Affects:** `dialogue/orchestrator.py`, `dialogue/state.py`. This is exactly the kind of correctness bug the plan's "run it, don't just write it" testing philosophy is meant to catch before a policy like `AFTER_NTH_REPEAT` — one of the three arms the eventual RCT needs — silently never worked.

### D29 — Dialogue-gate testing uses `fakeredis`, not a live Redis server
**Decision:** Unit tests for `dialogue/state.py` and `dialogue/orchestrator.py` run against `fakeredis.FakeAsyncRedis` — an in-memory, Redis-protocol-compatible implementation — rather than skipping gracefully the way Postgres-dependent integration tests do.
**Why:** This sandboxed dev environment has neither Docker nor a local Redis install (same constraint noted for Postgres since the Phase 1 DB-layer commit). Unlike Postgres, where a graceful-skip pattern was the pragmatic choice (SQL dialect/constraint behavior genuinely needs a real Postgres to verify), Redis usage here is simple enough (get/set/delete with JSON string values) that a well-maintained fake client gives *real* coverage of the actual state-machine logic — which is the most important, most bug-prone part of Phase 3 — rather than 100% of dialogue-state tests skipping locally. `docker-compose.yml`'s real Redis service remains what's used in the actual dev/deploy environment; `fakeredis` is a test-only dependency.
**Affects:** `pyproject.toml` dev dependencies (`fakeredis`), `tests/unit/dialogue/test_state.py`, `tests/unit/dialogue/test_orchestrator.py`.

### D30 — SSE event stream separates structured diagnostic events from the one gated child-facing text event
**Decision:** `POST /sessions/{id}/steps` streams four event types: `verdict` and `classification` (structured, internal/diagnostic — not gated, since they're not generated prose shown as a tutor message), `message_chunk` (the only event carrying LLM-generated child-facing text, emitted only after `handle_step_submission()` has already cleared both output gates), and `turn_complete` (final structured summary). "Streaming" for now means word-chunking an already-fully-vetted complete message string, not real token streaming.
**Why:** technical_architecture.md §6's "never stream an unvetted draft" rule applies specifically to generated dialogue text — not to structured verifier/classifier output, which was never a candidate for leakage/readability gating in the first place (it's not prose a child reads). Keeping these as separate, clearly-labeled event types means a real chat UI (Phase 4) can choose to render only `message_chunk`/`turn_complete.message` as tutor bubbles and ignore `verdict`/`classification` as the diagnostic channel they are, rather than the gate boundary being implicit or easy to violate by accident.
**Affects:** `api/routes/sessions.py`. Real Groq token streaming (once a key exists) replaces the post-hoc word-chunking without changing the SSE event shape — `message_chunk` events would just start arriving incrementally from the actual `generate()` call instead of being sliced from a complete string after the fact.

### D31 — `GET /problems/{id}` returns a sanitized `PublicProblem`, never the raw internal `Problem`
**Decision:** The frontend needs to know a problem's step-graph *shape* (step ids, types, `next` pointers) to decide which widget to render next, but a new `PublicStepNode`/`PublicProblem` pair (backend `api/routes/problems.py`) deliberately omits `expected_state` on every node and omits `final_answer` entirely. `given` (the input numbers, e.g. minuend/subtrahend) is included — that's not secret, it's what's already shown to the student on the problem itself.
**Why:** This was caught while building the frontend, before it shipped: a naive `GET /problems/{id}` returning the full internal `Problem` — which is exactly what the verifier and seed loader use internally — would hand every correct answer for every step straight to the browser, readable in devtools by any student. That directly undermines the entire premise of the leakage filter (D8): it's pointless to gate LLM-generated messages against revealing the answer if the REST API serves the answer key on the side. `test_public_problem_endpoint_never_exposes_answers` (backend `tests/integration/test_api.py`) asserts this directly — including a literal string-search of the raw response body for the numeric final answer.
**Affects:** `api/routes/problems.py` (backend), `frontend/src/types.ts`'s `PublicProblem`/`PublicStepNode`, `frontend/src/frontier.ts`. The frontend's own DAG-frontier computation (`computeFrontier`) intentionally re-derives the same union-of-`next` logic as the backend verifier's `_frontier()` purely to decide *which widget to offer* — it has zero bearing on correctness; the backend independently re-verifies from scratch on every submission regardless of what the frontend thinks the frontier is (D1, D15).

### D32 — Frontend widgets are tap-only; no free-text/numeric typing anywhere in the step-input path
**Decision:** Every structured field (column, single digits, two-digit-range borrow values, the boolean borrow flag) is entered via a dedicated tap component (`DigitPad`, `ColumnPicker`, `BooleanToggle`, `Stepper`) — there is no `<input type="text">` or `<input type="number">` anywhere in the four step widgets. `<fieldset>`+`<legend>` provides the accessible group semantics natively; an earlier draft duplicated this with an explicit `role="group" aria-label`, which produced two identically-named accessible groups and was caught by a failing component test (`CompareColumnWidget.test.tsx`) before being fixed.
**Why:** Direct implementation of D12/D13 — Shih et al. 2023's real 6th-grade deployment found keyboard/mouse input "time-consuming and inconvenient" for this age group. `write_final_answer` is the one field that's inherently multi-digit (the final numeric value); rather than a text field, the widget derives `value` automatically by summing tapped per-column digits at their place value, so the student never types a multi-digit number directly either.
**Affects:** `frontend/src/components/widgets/*`. `WriteFinalAnswerWidget` covers only units/tens/hundreds/thousands (4 columns) — sufficient for all 6 seeded problems (widest is 4 digits before the leading-zero drop in problem 004) but a documented scope limit, not a hidden one, if a wider problem is added later.

### D33 — Frontend verification: build/lint/typecheck/test all pass; full browser interaction against the live backend could not be verified in this environment
**Decision:** Phase 4's frontend was verified via: `npm run typecheck` (clean), `npm run lint` (clean), `npm test` (17/17 component/unit tests passing — SSE parsing including a chunk-boundary-split event, DAG frontier computation, widget tap-interaction and submitted-field-shape assertions), `npm run build` (production build succeeds), and starting the Vite dev server and confirming via `curl` that it serves the expected HTML shell and correctly transpiles `main.tsx` (HTTP 200). **What was not verified**: actually opening the app in a browser and clicking through the golden-path flow against a live backend. This sandbox has neither a browser/screenshot tool nor Docker (so no live Postgres/Redis/API to point the frontend at) — the same constraint noted for every Postgres/Redis-dependent backend test this project (flagged honestly rather than silently skipped or claimed as done).
**Why:** CLAUDE.md requires starting the dev server and using the feature in a browser before reporting UI work complete, and explicitly requires saying so plainly when that isn't possible rather than claiming success. This is that disclosure, not a workaround.
**Affects:** Phase 4 close-out. **Before treating the prototype checkpoint as fully confirmed**, Arnav (or anyone with Docker available) should run `docker compose up`, then `cd frontend && npm run dev`, and walk through: solving the canonical problem correctly step-by-step, deliberately triggering each of the four seeded bugs (B1-B4) and confirming Socratic dialogue appears, confirming turn-budget escalation shows a worked example after repeated wrong attempts, and confirming a correct retry resolves the dialogue and lets the student continue.

### D34 — Real infrastructure obtained without Docker: `pgserver` (portable Postgres) + `fakeredis`'s real TCP server, for actual end-to-end verification
**Decision:** To verify the stack "like a real user" without Docker/WSL available in this environment, real Postgres came from `pgserver` (a pip-installed, self-contained Postgres binary — no system service, no admin rights, a real `postgres.exe` process on a real TCP port) and real Redis-protocol service came from `fakeredis.TcpFakeServer` (an actual TCP listener implementing the Redis wire protocol, not the in-process `FakeAsyncRedis` used in unit tests — the app's real `redis.asyncio.Redis` client talks to it exactly as it would talk to real Redis). Both are one-off, local-only conveniences for this verification session (`.local-e2e/`, gitignored) — `docker-compose.yml`'s `postgres`/`redis` services remain the real dev/deploy path.
**Why:** The alternative was continuing to report "verified via mocks and graceful-skips" indefinitely. Running against real services immediately surfaced three genuine bugs (D35) that no amount of mocked or skipped testing could have caught — this is exactly the value "test like a real user" was asking for.
**Affects:** Nothing in the shipped app; this is a verification-session artifact, not a new project dependency (`pgserver`/`fakeredis`-as-a-server aren't imported by any application code).

### D35 — Three real bugs found and fixed only by running against real Postgres + Redis together
**Decision / findings:**
1. **Cross-event-loop asyncpg connection reuse.** `db/base.py` creates its engine/session-factory once at *module import time*, which is correct for a real deployed process (uvicorn runs one event loop for the process's whole life) but breaks under pytest-asyncio's default per-test-function event loop: a connection first used under one test's loop gets reused by a later test's *different* loop, corrupting the asyncpg connection (`InterfaceError: cannot perform operation: another operation is in progress`). Every integration test touching a route failed with this once actually run against a real DB — previously they only ever hit the Postgres-unreachable skip path, so this was invisible. **Fixed** by setting `asyncio_default_fixture_loop_scope = "session"` and `asyncio_default_test_loop_scope = "session"` in `pyproject.toml`'s pytest config, so the whole test session shares one event loop — matching production's actual one-loop-per-process reality, not working around a testing-only quirk with testing-only code.
2. **A generic round-trip test collided with real seed data.** `test_step_type_round_trips` (`tests/integration/test_migrations.py`) inserted a `("subtraction_with_borrowing", "borrow")` `StepType` row to test the ORM mapping — a real pair that CI's own migrate-then-seed-then-test order (`.github/workflows/ci.yml`) already populates by the time this test runs, violating the unique constraint. This test had literally never been run in that real order before now. **Fixed** by using synthetic (`_test_topic`/`_test_step_type`) data — the test's actual intent (does the model round-trip through Postgres) never needed a real seeded value.
3. **pytest module-collection collision.** `tests/unit/classification/test_classifier.py` and `tests/integration/test_classifier.py` share a basename with neither directory packaged (no `__init__.py`), which pytest's default (`prepend`) import mode resolves by sys.path insertion — fine when `unit` and `integration` are invoked as separate `pytest` processes (as CI does), but breaks the moment both are collected in one run (e.g. `pytest tests/`, `pytest .`, or any future CI consolidation), with "import file mismatch." **Fixed** by setting `addopts = "--import-mode=importlib"` (pytest's modern recommended mode, which resolves modules by fully-qualified path instead of sys.path/basename), rather than working around it with `__init__.py` files or forced-unique filenames.
**Why this belongs in the architecture record, not just the changelog:** all three were latent from the moment they were written (as early as Phase 1) and every single "N tests, all skipping gracefully / all passing on mocks" report across every phase was accurate *for what it tested* but could not have caught any of these — they only exist at the boundary where deterministic-but-untested-together pieces (module import timing, CI job ordering, filesystem layout) actually interact. This is the concrete argument for why "tested like a real user" was worth doing before calling the prototype checkpoint trustworthy, not just a formality.
**Affects:** `backend/pyproject.toml` (pytest config), `backend/tests/integration/test_migrations.py`. All 161 unit+golden+integration tests pass together, in one run, against real Postgres and real Redis, as of this fix.

### D36 — Two more real bugs found only by actually driving the frontend in a real browser against the live backend
**Decision / findings**, both found via a real headless-Chromium (Playwright) session clicking through the actual golden path against the live `uvicorn`+real-Postgres+real-Redis stack, not against mocks or component-test assertions alone:
1. **`SubtractColumnWidget`'s minuend-digit field couldn't represent its own real value range.** After any borrow, a column's minuend digit is legitimately 10-19 (e.g. the canonical 52-25 problem's units column becomes 12) — but the widget used `DigitPad`, which only offers single digits 0-9. A real student could never have correctly completed a `subtract_column` step following a borrow, in every seeded problem except the one with no borrow at all. Caught the moment the driver script tried to enter "12" and there was no such button. **Fixed** by switching that one field to `Stepper` (the same +/- control `BorrowWidget` already used for its own 0-19-range fields), confirmed visually in a real screenshot showing "12" correctly entered and submitted.
2. **The step-type tab never advanced past an already-completed step.** The backend's frontier deliberately keeps an already-accepted step's type nominally reachable (D11 — no exclusion, only de-prioritization). `StepWidgetSwitcher`'s tab-selection state had no way to know this and simply kept whatever tab was already active, which defaulted to the *first* type in graph order — so a student who correctly finished "Borrow" was left looking at the Borrow widget again instead of advancing to "Subtract." Caught by watching the actual rendered screenshot after a real borrow submission. **Fixed** by adding a `preferredStepType` prop (`ProblemSolver` computes it as the type of the node immediately following the most-recently-accepted step) that `StepWidgetSwitcher` adopts via a `useEffect` keyed only on that prop — advancing the active tab exactly when a new step is genuinely accepted, without fighting a user's manual tab click mid-fill-in.
**Why this belongs here, not just the changelog:** both bugs were invisible to every prior verification method used in Phase 4 — `tsc`, ESLint, and component tests that render a widget in isolation with hand-picked props all passed the whole time, because none of them exercise the *sequence* of real user actions against real backend responses where these two bugs actually live (a value the mocked widget tests never generate; a state transition the isolated-render tests never trigger). This is the frontend half of the same argument D35 makes for the backend.
**Affects:** `frontend/src/components/widgets/SubtractColumnWidget.tsx`, `frontend/src/components/StepWidgetSwitcher.tsx`, `frontend/src/components/ProblemSolver.tsx`. Both have dedicated regression tests now (`SubtractColumnWidget.test.tsx`'s 12-value case; `StepWidgetSwitcher.test.tsx`'s tab-advancement case).

## Implementation-phase decisions (from the approved Phase 1–4 build plan, 2026-08-13)

### D21 — Repo layout: `backend/` (Python) and `frontend/` (React/TS) as siblings from commit one; `verification/topics/<topic>/` as the per-topic extension point
**Decision:** All Python lives under `backend/src/studyhelp/`, with `frontend/` created as an empty placeholder immediately rather than added later. Within the backend, each pipeline stage gets its own package (`db/`, `schemas/`, `verification/`, `classification/`, `dialogue/`, `llm/`, `api/`, `seed/`); `classification/` and `dialogue/` exist as empty stub packages from Phase 1 even though they're not filled in until Phases 2–3. Adding a new topic to the verifier means adding a new module under `verification/topics/<topic>/` against the shared `StepVerifier` interface — never touching pipeline code.
**Why:** Avoids a painful path/CI/Docker-context restructure when Phase 4's frontend actually lands (`frontend/` already exists, already has its own place in `docker-compose.yml`'s eventual shape). Stub packages for later phases mean Phase 2/3 slot in without moving files Phase 1 code already imports from. This is the concrete mechanism behind the already-settled "adding a topic = new verifier module, not touching the pipeline" principle (`CLAUDE.md`, D1).
**Affects:** All backend code; directly followed from a Plan sub-agent's design pass grounded in `docs/technical_architecture.md` §§1–3.

### D22 — Confidence thresholds are named constants with dedicated test coverage, not implicit behavior
**Decision:** `ACCEPT_THRESHOLD=0.9` and `REJECT_THRESHOLD=0.75` are named constants in `verification/confidence.py`. Exact frontier match → valid, high confidence. Exact non-adjacent-but-graph-valid match → valid, flagged `non_adjacent_valid_match` (accepted, not silently absorbed — surfaced for review per D11). Unambiguous field mismatch scoring ≥ `REJECT_THRESHOLD` confidence-of-wrongness → invalid. Anything in the band between the two thresholds, or genuinely ambiguous → **don't interrupt** (`low_confidence_passthrough`), but still logged as an event so the threshold can be tuned from real data later.
**Why:** Makes D2's "bias toward false negatives" an actual tested code path with its own golden-suite cases, not an emergent property nobody can point to in a review. A malformed/nonexistent step type is the one exception carved out of the false-negative bias — that's a structural error, not an ambiguous math judgment, so it always rejects regardless of confidence.
**Affects:** `verification/confidence.py`, `verification/topics/subtraction_borrowing/verifier.py`, golden regression suite (dedicated pass-through test cases).

### D23 — `verify_step()`'s procedural correctness is custom graph/state-machine logic; sympy's role is narrow and explicit
**Decision:** For subtraction-with-borrowing, sympy is used for exactly two things: (a) an independent cross-check of the final arithmetic identity (`minuend - subtrahend == final_answer`) that doesn't trust the graph-walk alone, and (b) per-step arithmetic identities within a candidate node (e.g. `to_digit_after == to_digit_before + 10`). Whether the *right procedural move happened in the right place* — was a borrow needed here, did the student borrow from the correct column, does this step land on a valid DAG node — is custom Python logic (candidate search over graph nodes + per-step-type field checkers), not sympy.
**Why:** Being explicit about this split matters: sympy's arithmetic contribution for plain integer subtraction is fairly thin on its own (plain ints would mostly do), so its real value here is (i) a shared, reusable arithmetic-identity utility that later topics (fractions, LCM/HCF) will lean on far more heavily, and (ii) a second, independent check on the final answer that doesn't trust the DAG-walk as the only source of truth. Avoids the false impression that "sympy verifies subtraction-with-borrowing" when the actual procedural verification is bespoke.
**Affects:** `verification/topics/subtraction_borrowing/sympy_utils.py`, `step_checkers.py`.

### D37 — Second topic slice (`fractions_addition`) built with free-text step input, superseding D12 for this topic only
**Decision:** At the founder's explicit request (not a Phase 0 syllabus-audit pick — this bypassed the normal "propose and confirm" sequencing step described in CLAUDE.md, by direct instruction), a second topic slice was added: NCERT Class 5 fraction addition (like/unlike denominators), decomposed into `rewrite_common_denominator` → `add_numerators` → `simplify_fraction` → `write_final_answer`. The student types each step into a plain text box (one box per step, "+ Next step" advances and triggers verification) instead of using a structured math-aware widget. A new deterministic grammar (`verification/topics/fractions_addition/free_text_parser.py`) parses exactly the shapes each step type can legally take (`a/b`, `a b/c`, `a/b + c/d`, `a/b - c/d`) via regex — not a general expression evaluator, and never handed to the LLM. Anything outside the grammar fails closed as `ErrorSignal(kind="malformed")`, identically to how `pydantic.ValidationError` fails closed for structured-widget topics.
**Why:** The founder weighed the notation-ambiguity risk D12 was written to avoid against the product requirement (asked for directly: "text boxes for each step... verify when I move to next step... interrupt user there") and chose to accept a narrow, grammar-constrained parser rather than a general one. This is confirmed narrower than a full free-text math parser: it's four fixed regex shapes per step type, not `eval()` or an LLM-based interpreter, so it preserves D1's "LLM is never the arbiter of correctness" and D12's underlying worry (notation-ambiguity bugs) is addressed by rejecting anything off-grammar rather than by guessing at intent.
**Affects:** `verification/topics/fractions_addition/*` (new module), `schemas/verify.py` (`VerifyResult.parsed_fields`, D38), `frontend/src/components/FreeTextStepper.tsx` (new component), `seed/fixtures/{step_types,problems,misconception_bank,buggy_rule_library}` (fractions entries), `seed/loader.py` (`_ARITHMETIC_VALIDATORS` dict, D39).

### D38 — `VerifyResult.parsed_fields` bridges free-text topics' raw wire fields to the structured shape classification/dialogue need
**Decision:** `VerifyResult` gained an optional `parsed_fields: dict[str, Any] | None` field. Structured-widget topics leave it `None` (their `StudentStep.fields` is already the structured shape). Free-text topics populate it with whichever candidate step type's parse the verifier used — `api/routes/sessions.py` does `structured_student_fields = verify_result.parsed_fields or request.student_step.fields` once, and passes that (not the raw `{"text": ...}`) into both `classify_error()` and `handle_step_submission()`.
**Why:** Without this, the buggy-rule matcher and LLM decide/generate calls downstream would receive `{"text": "4/12"}` instead of `{"num": 4, "den": 12}` — every fraction-topic buggy-rule signature (F1/F2/F3) needs the parsed numeric fields to pattern-match at all. Considered re-parsing the raw text a second time inside the classifier instead, but that duplicates the grammar in two places and can disagree with what the verifier actually matched against; having the verifier (which already did the parse to produce its verdict) hand the result forward is a single source of truth.
**Affects:** `schemas/verify.py`, `api/routes/sessions.py`, `verification/topics/fractions_addition/verifier.py`.

### D39 — Per-topic seed-time arithmetic validation became a dispatch dict once a second topic existed
**Decision:** `seed/loader.py`'s `load_problems()` previously imported `subtraction_borrowing`'s `validate_problem_arithmetic` directly and called it unconditionally (documented at the time, D19, as a deliberate "don't front-load" simplification for a single-topic codebase). It's now `_ARITHMETIC_VALIDATORS: dict[str, Callable]`, keyed by `problem.ncert_ref.topic`, with `fractions_addition`'s own `validate_problem_arithmetic` (sympy `Rational`-based, checking common-denominator equivalence, addition arithmetic, and simplification arithmetic against the DAG) added alongside it.
**Why:** This is exactly the sequencing D19 anticipated — the dict is what "don't front-load" was deferring, not a redesign. No behavior changed for the subtraction topic.
**Affects:** `seed/loader.py`, `verification/topics/fractions_addition/sympy_utils.py`.

### D41 — Full 14-chapter syllabus + universal free-text input, founder override of D19 and D12/D32 (2026-08-15)
**Decision:** On the founder's direct instruction (same mechanism as D37's precedent — explicit, in-conversation, not a Phase 0 pick), this build covers the entire NCERT Class 5 Math-Magic syllabus (10 problems/chapter, 140 total) instead of sequencing a narrow slice, and makes free-text step input universal — including converting the existing tap-widget `subtraction_borrowing` topic — instead of keeping structured widgets as the default. Of the 14 chapters, 7 (subtraction, fractions, LCM/HCF, decimals, area/perimeter, multiplication/division, measurement) get the existing full-DAG treatment; the other 7 (Shapes & Angles, How Many Squares?, Does it Look the Same?, Patterns, Mapping, Boxes & Sketches, Smart Charts — already named as non-DAG in D20's audit) get a **light 1-2 step text-answer check** instead of a forced procedural DAG, per the founder's explicit choice among the options presented.

**Decision:** `llm/prompts.py`'s `TUTOR_PERSONA` (warm, patient, plain English, no Hindi/Indian-household code-switching — the founder's explicit choice over the alternative offered) is shared by new `DECIDE_SYSTEM_PROMPT`/`GENERATE_SYSTEM_PROMPT` constants, used by both `GroqLLMProvider.decide()` and `.generate()` (previously `NotImplementedError` stubs, now implemented against the same JSON-mode chat-completions shape `classify()` already used). `GROQ_MODEL=llama-3.3-70b-versatile` was **verified live**, not assumed — `backend/scripts/verify_groq_structured_output.py` fired one real `classify`/`decide`/`generate` call each against the actual Groq API and confirmed every response parses as valid structured output with no leaked correct-answer value. ### D43 — Universal free-text frontend: tap widgets removed, `FreeTextStepper` is the only step-input component, `display_label` + `GET /problems` catalog added (2026-08-15)
**Decision:** `StepWidgetSwitcher` and every structured tap widget (`DigitPad`, `ColumnPicker`, `BooleanToggle`, `Stepper`, `CompareColumnWidget`, `BorrowWidget`, `SubtractColumnWidget`, `WriteFinalAnswerWidget`) are deleted, not deprecated in place — D41 already established free-text as universal, and CLAUDE.md's own standard is to delete code once certain it's unused rather than leave it as a parallel path. `FreeTextStepper` (previously fractions-only) is now the only step-input component for every topic; it takes a `hint?: string` prop instead of a hardcoded placeholder string. `ProblemSolver.tsx` drops all topic-branching (`FREE_TEXT_TOPICS`, `isFreeTextTopic`) entirely. `StudentStep.step_type` collapses to a single fixed literal (`"free_text_step"`) since the backend's free-text verifiers already infer the actual step type from the DAG frontier by trying each reachable type's grammar against the typed text (established by `FractionsAdditionVerifier`) — the wire value was never actually read.

Two backend additions support this: (1) `PublicStepNode.hint` (sourced from that step type's `step_types.description` fixture) is what lets `FreeTextStepper` show a meaningful, topic-specific placeholder without the frontend hardcoding anything about any topic. (2) `Problem.display_label` (new required field, backfilled onto all 10 existing problem fixtures, migration `0003_problem_display_label.py`) plus a new `GET /problems` catalog endpoint (`ProblemSummaryOut` — problem id, `ncert_ref`, `display_label`, deliberately no step graph or `given`) replace `App.tsx`'s hardcoded `DEMO_PROBLEMS` array, which was explicitly flagged as a dev-only stopgap the moment 140 problems across 14 chapters made a hardcoded list impractical. `App.tsx` is now a two-level chapter → problem picker driven by the real catalog.

**A real data bug was caught and fixed while adding `display_label`, not left in place**: all 4 existing `fractions_addition` problem fixtures had `ncert_ref.chapter=7, chapter_title="How Many Squares?"` — wrong on both counts (fractions is NCERT Ch.4 "Parts and Wholes"; Ch.7 is "Can You See the Pattern?"). Corrected to `chapter=4, chapter_title="Parts and Wholes"` in the same pass, since Phase D's fraction-topic expansion depends on this metadata being right.
**Why:** Direct implementation of D41 (universal free-text) plus a practical consequence of covering the full syllabus — a hardcoded problem list and fraction-specific heading-reconstruction logic in `ProblemSolver.tsx` (`given.a_num`/`given.minuend` branching) do not scale past a couple of demo topics, and `display_label` removes that topic-specific reconstruction entirely (the heading is now just `problem.display_label`).
**Affects:** `frontend/src/components/` (widgets deleted), `frontend/src/App.tsx`, `frontend/src/components/ProblemSolver.tsx`, `frontend/src/components/FreeTextStepper.tsx`, `frontend/src/types.ts`, `frontend/src/api/client.ts`, `backend/src/studyhelp/api/routes/problems.py`, `backend/src/studyhelp/schemas/step_schema.py`, `backend/src/studyhelp/db/models/problem.py`, `backend/alembic/versions/0003_problem_display_label.py`, all 10 existing problem fixtures.
**Supersedes:** D12/D32 for the `subtraction_borrowing` topic specifically (previously the one remaining structured-widget topic) — completing D41's project-wide supersede in code, not just in decision.

### D44 — `subtraction_borrowing`'s verifier ported to free text while preserving its whole-graph, threshold-biased matching (not fractions' frontier-only, always-reject approach) (2026-08-15)
**Decision:** `verification/topics/subtraction_borrowing/free_text_parser.py` (new) defines one small regex grammar per step type (`compare_column`: `"<column> <top> < <bottom>"`/`">="`; `borrow`: `"<from_column> <before>->{after}, <to_column> <before>->{after}"` with an optional `", result <digit>"` suffix for the combined-action alt-path node; `subtract_column`: `"<column> <top> - <bottom> = <result>"`; `write_final_answer`: the bare final number, decomposed into a per-column `digits` dict by place value). `SubtractionBorrowingVerifier.verify_step()` now tries every step type's grammar against the submitted text (the `fractions_addition` pattern) instead of trusting a client-declared `step_type`.

Two things were *deliberately not* copied from the fractions verifier, because this topic's already-tested behavior depends on them: (1) candidate search still covers every node of a matched type across the **whole graph**, not just the DAG frontier — a step type like `subtract_column` legitimately recurs once per column, unlike every fractions step type appearing exactly once; (2) near-match resolution keeps the `REJECT_THRESHOLD` field-agreement passthrough bias (D22) instead of always rejecting a non-exact parse — this topic's 30-case golden suite (including the B4 stale-borrow-digit passthrough case, a deliberate documented finding) already exercises this exact threshold behavior, and porting the input mechanism must not silently change it.
**Why:** Completes D41/D43's universal free-text conversion for the one remaining structured-widget topic, without regressing this topic's already-tuned confidence behavior — verified directly: the full existing golden suite (regenerated as free text via a new `render_student_text()` inverse function, same 30 cases, same case semantics) and the fixture-arithmetic walkthrough test both pass unchanged.
**Affects:** `verification/topics/subtraction_borrowing/{free_text_parser.py (new), verifier.py, step_checkers.py (parse_student_fields removed, now dead)}`, `scripts/build_golden_cases.py`, `tests/unit/verification/test_subtraction_borrowing_{verifier,parser}.py`, `tests/unit/verification/test_problem_fixtures_walkthrough.py`, `tests/integration/{test_api,test_sessions_api}.py`.

### D45 — `fractions_addition` expanded to cover NCERT Ch.4's full scope (subtraction, comparison); package/topic name kept as-is (2026-08-15)
**Decision:** The `fractions_addition` topic now covers addition, subtraction, and comparison of like/unlike-denominator fractions — NCERT Ch.4 "Parts and Wholes"'s actual scope, not just addition. Two new step types: `subtract_numerators` (identical `{num, den}` shape to `add_numerators`, reusing its field model and free-text grammar) and `compare_fractions` (new `{left_num, left_den, op, right_num, right_den}` shape, `op` ∈ `{"<", ">", "="}`, grammar `"a/b < c/d"` etc). A comparison problem is a deliberately **shorter, 1-step DAG** (`compare_fractions` is both entry and terminal) — not every problem in a chapter needs the same procedural depth as the 4-step add/subtract chain, and forcing an artificial intermediate step onto a genuinely single-judgment task would be padding, not rigor. `sympy_utils.validate_problem_arithmetic()` now dispatches on a new `given["op"]` field (`"+"`/`"-"`/`"compare"`, defaulting to `"+"` so the original 4 fixtures need no changes) rather than assuming addition unconditionally.

The Python package (`verification/topics/fractions_addition/`) and the `topic` string itself (`"fractions_addition"`, used throughout the DB, fixtures, and this file's D37-D40 entries) were **not** renamed to something scope-neutral like `"fractions"`. This was a deliberate scope cut, not an oversight: renaming touches ~15+ files (fixture topic strings, `_ARITHMETIC_VALIDATORS` dict key, every existing ARCHITECTURE.md/CHANGELOG.md cross-reference) for a purely cosmetic gain, with real risk of missing a reference under time pressure — the `topic` string is an internal identifier, not user-facing copy (D43 already made the frontend fully topic-agnostic, so no UI text depends on this name either).
**Why:** Direct implementation of the founder's full-syllabus scope (D41) applied to the fractions chapter specifically — 10 problems requires more than one operation to be a faithful "10 questions covering the chapter," and NCERT Ch.4 genuinely covers all three of these skills, not just addition.
**Affects:** `verification/topics/fractions_addition/{step_checkers,free_text_parser,sympy_utils,verifier}.py`, `classification/rule_matcher.py` (2 new matchers: F4 subtract-across, F5 compares-numerators-only — both dynamically covered by the existing cross-matrix test), `dialogue/leakage_filter.py` + `dialogue/orchestrator.py::_protected_values()` (widened to also protect `compare_fractions`' non-numeric `op` answer — see D46), 6 new problem fixtures (`fractions-sub-001..003`, `fractions-cmp-001..002`, plus one more addition problem `fractions-add-005`), expanded misconception bank / buggy-rule library (9 entries total, up from 3).

### D46 — Leakage filter widened to protect non-numeric answers (comparison symbols), not just numbers (2026-08-15)
**Decision:** `dialogue/leakage_filter.py::contains_leakage()`'s `protected_values` parameter widened from `list[int]` to `list[int | str]` — numeric values still matched via the existing bare-number regex; string values matched by direct substring containment. `dialogue/orchestrator.py::_protected_values()` now also includes a step's `op` field when it's a comparison symbol (`"<"`/`">"`/`"="`), never when it's `"+"`/`"-"` (an addition/subtraction problem's operation is already visible to the student in the problem statement — not secret; only a comparison's *result* is the actual answer).

### D47 — LCM/HCF topic slice; buggy-rule matcher interface limitation found and worked around (2026-08-15)
**Decision:** New `lcm_hcf` topic (NCERT Ch.6, "Be My Multiple, I'll Be Your Factor"), built by a delegated agent against the exact `fractions_addition` pattern (free-text, frontier-restricted, always-reject-on-non-exact-match per D40's rationale). **Why:** Direct implementation of D41 (full-syllabus expansion) for the LCM/HCF chapter. The interface-limitation finding is worth recording for future topic slices: **a candidate buggy rule must be checkable from one step's (correct, student) field pair alone** — if the bug's signature needs another step's or the problem's own context, it needs a different step's fields as the check target (as LH1/LH2 do), not a redesign of the matcher interface itself.

### D50 — Multiplication/division topic slice; scope fixed to 2-digit x 1-digit and exact-division only (2026-08-15)
**Decision:** New `multiplication_division` topic (NCERT Ch.13, "Ways to Multiply and Divide") — the richest DAG in the syllabus per D20's original audit. Built directly, not delegated (same reason as D49). Scope deliberately fixed to **2-digit × 1-digit multiplication with carrying** and **2-digit ÷ 1-digit exact division (no remainder)** — `validate_problem_arithmetic()` raises if a fixture falls outside this range. The digit-range scope cut avoids the conditional-DAG-shape complexity a fully general "any digit count" version would need, for a chapter where the pedagogical point (carrying in multiplication, bringing-down in division) is already fully demonstrated at 2-digit × 1-digit / 2-digit ÷ 1-digit.

### D40 — Fraction verifier's near-match confidence doesn't reuse subtraction's `REJECT_THRESHOLD` ratio
**Decision:** Subtraction's near-match resolution uses `REJECT_THRESHOLD` (0.75) against a field-agreement ratio (matched/total fields) — below it, the verifier passes the step through as valid rather than risk a false accusation (D2's false-negative bias). The fractions verifier does not reuse this: every fraction step type has only 2-5 fields, so a single wrong value already swings agreement to ~0.6-0.8, which would silently let exactly the seeded misconceptions (F1 no-common-denominator, F2 add-across, F3 forgot-to-simplify) pass through unflagged — defeating the point of seeding them. Instead: `evaluated` only ever contains candidates whose text already parsed cleanly into that step type's exact grammar (shape-level ambiguity is handled separately, one level up, as `ErrorSignal(kind="malformed")`), so a non-exact value match at that point is unambiguous, not low-confidence noise — the fractions verifier always rejects it.
**Why:** D2's false-negative bias exists to protect against wrongly telling a correct child they're wrong under genuine ambiguity. Once the text has already matched a step type's exact grammar, there's no such ambiguity left to protect against — the shape question and the value question are cleanly separated for this topic in a way they aren't for subtraction's flat multi-field digit comparison. Caught by writing this topic's own tests: the ported threshold-based logic let the F1 and F3 example bugs pass as "valid" in a first pass.
**Affects:** `verification/topics/fractions_addition/verifier.py::_resolve_near_match`. `verification/confidence.py`'s `REJECT_THRESHOLD`/`NON_ADJACENT_MATCH_CONFIDENCE` remain unchanged and still govern the subtraction topic.

### D52 — A confirmed buggy-rule match overrides `REJECT_THRESHOLD`'s low-confidence passthrough (2026-08-18)
**Decision:** D40 already flagged the exact risk this closes: subtraction's `REJECT_THRESHOLD`-gated field-agreement passthrough can let a real, known misconception through silently, because the fuzzy agreement ratio and "is this a genuine error" are different questions. Confirmed live: submitting the textbook B1 (`smaller-from-larger`) borrow-bug — a case the buggy-rule library exists specifically to catch — produced `is_valid=True, note="low_confidence_passthrough"` with zero feedback to the child, because `api/routes/sessions.py` only ever called `classify_error()` (which runs the deterministic rule matcher first) inside the `is_valid == False` branch. The rule matcher never even got a chance to look at the case it was built for. Fixed without touching D2/D22's threshold itself: `_pipeline_events()` now also attempts classification whenever the verdict is a passthrough field-mismatch (`is_passthrough_mismatch`), and if that classification resolves via `source == "rule"` (a deterministic, exact signature match — never the fuzzy LLM path), a dialogue-only copy of the verdict (`effective_verify_result`) is flipped to `is_valid=False` before reaching `handle_step_submission()`. The raw "verdict" SSE event already streamed to the client stays the verifier's honest, unmodified signal — only the *dialogue* decision changes.
**Why:** The false-negative bias (D2) is meant to protect against wrongly interrupting a child under genuine ambiguity. A confirmed buggy-rule signature match isn't ambiguous — it's exact, deterministic pattern matching, a fundamentally different (and more trustworthy) kind of confidence than a raw field-agreement ratio. Gating rule-matching *behind* the fuzzy threshold, rather than letting it run independently, meant the more precise signal was never consulted for exactly the passthrough cases where it mattered most. A genuinely ambiguous passthrough with no rule match (e.g. B4's deliberate stale-borrow-digit case, D22) still passes through silently, unchanged.
**Affects:** `api/routes/sessions.py::_pipeline_events`. No change to `verification/confidence.py`, `subtraction_borrowing/verifier.py`, or any other topic's verifier — this is purely a pipeline-wiring fix at the classification/dialogue boundary, not a verifier-confidence change.

### D53 — SSE pipeline degrades gracefully on an LLM-stage failure instead of crashing the stream (2026-08-18)
**Decision:** `classify_error()`'s LLM fallback and `handle_step_submission()`'s decide/generate calls can raise (provider outage, invalid model, rate limit) — confirmed live by pointing `GROQ_MODEL` at a nonexistent model: the exception propagated unhandled through the SSE generator, and the connection died mid-stream with no `error` frame, right after a real verdict had already streamed. The verifier's verdict (D1: the LLM is never the arbiter of correctness) was never at risk, but the child-facing half of the pipeline just silently broke. Fixed by wrapping the classification/dialogue stage of `_pipeline_events()` in a broad `try/except`: on failure, log the exception, yield one `message_chunk` + `turn_complete` pair carrying a safe, generic "having trouble thinking, try again" message, and commit the already-logged `step_submitted`/`verdict` events before returning — the research/observability data for this step submission is preserved even when the LLM stage fails outright.
**Why:** D14's turn-budget graceful-fallback principle (worked example on exhaustion) implicitly assumed the LLM stage *runs*, just runs out of turns — it didn't cover the LLM stage failing to run at all. An infra failure deserves the same "never leave the child stuck with a silently broken input box" treatment as turn-budget exhaustion, just with a generic message instead of a worked example (no `correct_fields`/`decision` context is guaranteed to exist at the point of failure).
**Affects:** `api/routes/sessions.py::_pipeline_events` (new `_LLM_UNAVAILABLE_MESSAGE`, try/except wrapping the classify+dialogue stage). No change to `dialogue/orchestrator.py`'s own turn-budget escalation path, which is unaffected and still produces a real worked example when it *does* run.

### D55 — Seed loader reads fixture JSON as UTF-8 explicitly, not the platform default (2026-08-18)
**Decision:** `seed/loader.py::_load_json` called `path.read_text()` with no `encoding=` argument. On Windows, `Path.read_text()`'s default encoding is the process's locale encoding (cp1252 in this environment), not UTF-8 — every fixture JSON file is authored and saved as UTF-8, so any non-ASCII character (the `−` minus sign in `display_label`s like `"52 − 25 (single borrow)"`) got silently mis-decoded on load and stored corrupted in Postgres (`52 â€' 25` reaching the browser). Fixed with `path.read_text(encoding="utf-8")`.
**Why:** A one-line platform-dependent default silently corrupting non-ASCII text is exactly the kind of bug that's invisible in CI/Linux dev environments and only surfaces on Windows — worth naming explicitly here so it doesn't quietly reappear the next time a file-reading helper is added anywhere in this codebase. Fixed at the source (the loader) rather than downstream (e.g. re-encoding in the API layer), since the corruption happens at read time and every downstream consumer (DB, API, frontend) was otherwise correct.
**Affects:** `seed/loader.py::_load_json`. Required a full DB wipe/reseed (`alembic downgrade base && alembic upgrade head && python scripts/seed_db.py`) to clear already-corrupted rows — the fix only prevents new corruption, it doesn't repair existing rows.

### D56 — Gate-rejected dialogue retries carry concrete feedback and non-zero temperature, not a repeat of the same prompt (2026-08-18)
**Decision:** `dialogue/orchestrator.py`'s regeneration loop (D8/D9's leakage/readability gates, `MAX_GATE_REGENERATION_ATTEMPTS = 2`) called `llm_client.generate()` with the exact same `GenerateRequest` on every attempt. Confirmed live: a shapes_angles dialogue turn generated a message scoring 5.36 on Flesch-Kincaid (ceiling 5.0), got rejected, and regenerated — at `temperature=0` (used everywhere for determinism) with an unchanged prompt, the Groq provider reliably reproduced the *identical* text three times running, burning the entire retry budget on one guaranteed-repeat draft before falling back to the generic canned message. Fixed two ways together: (1) `GenerateRequest` gained an optional `regeneration_feedback: str | None` field; the orchestrator now sets it to a concrete, gate-specific instruction ("you leaked the answer, ask a question instead" / "too complex, use shorter simpler words") after each rejection, and `GENERATE_SYSTEM_PROMPT` gained a rule telling the model to treat this as a mandatory-rewrite signal, not just more context; (2) `GroqLLMProvider.generate()` now uses `temperature=0.6` (up from 0) whenever `regeneration_feedback` is set, so even a retry that doesn't fully act on the feedback still has a real chance at different phrasing. Attempt 0 (the common case) is untouched — still `temperature=0`, still no feedback field.
**Why:** A regeneration loop is only as useful as its ability to produce something different from what was just rejected. At `temperature=0`, an unchanged prompt is not a retry mechanism at all — it's a deterministic guarantee of the same rejection, three times, at three times the latency and Groq cost, for zero behavioral benefit over failing once. Both parts matter together: feedback alone could still be ignored by the model; temperature alone would vary phrasing without addressing *why* it was rejected.
**Affects:** `llm/client.py` (`GenerateRequest.regeneration_feedback`), `llm/providers/groq.py::generate/_chat_json` (temperature threading), `llm/prompts.py` (`GENERATE_SYSTEM_PROMPT` rule 7), `dialogue/orchestrator.py` (retry loop tracks and passes feedback per rejection reason). `llm/providers/mock.py` unaffected — the mock is deterministic by design regardless of this field.

### D57 — Leakage filter's `_protected_values()` had no coverage at all for word-answer step types (2026-08-18)
**Decision:** `dialogue/orchestrator.py::_protected_values()` extracts "the answer" from `correct_fields` via a fixed list of numeric-ish keys (`result_digit`, `value`, `num`, `den`, etc.) plus a special case for the fractions `op` symbol. The 7 light-check topics (D47 Phase F: shapes_angles, how_many_squares, symmetry, patterns, mapping, boxes_sketches, smart_charts — plus `patterns`' two step types specifically) all use `expected_state = {"answer": <word or number>}`, a key `_protected_values()` never checked. Confirmed live: a shapes_angles dialogue turn's generated message freely used the word "acute" mid-question with nothing to catch it, because `_protected_values({"answer": "acute"})` silently returned `[]` — the leakage filter had zero protected values to check the message against for roughly a third of the full syllabus (70 of 140 problems) by problem count. Fixed by adding an `answer` extraction (string values only, same treatment as `op`) to `_protected_values()`. While fixing this, also made `contains_leakage()`'s string-value matching case-insensitive (`value.lower() in message.lower()`) — a bare word like "acute" is far more likely to appear capitalized at a sentence boundary than a comparison symbol ever was, and the original case-sensitive check would have missed exactly that case.
**Why:** This is a leakage-filter *coverage* gap, not a logic bug in the matching itself — `contains_leakage()` always worked correctly for whatever it was given, but Phase F added a whole new answer shape (`{"answer": <str>}`) without extending the one function responsible for knowing what counts as "the answer" for a given step. CLAUDE.md's leakage-filter requirement is topic-agnostic by design specifically so a new topic doesn't need pipeline changes — this was the one spot where a new topic's answer *shape* (word vs. number) did need one, and it was missed until Phase F's topics were actually exercised end-to-end with a real LLM.
**Affects:** `dialogue/orchestrator.py::_protected_values` (+answer extraction), `dialogue/leakage_filter.py::contains_leakage` (case-insensitive string matching). ### D59 — `verify_step()` searches every reachable DAG node, not just the immediate frontier, for all 7 heavy (DAG) topics (2026-08-23)
**Decision:** Only `subtraction_borrowing/verifier.py` (Phase 1's original topic) ever searched the whole graph for an exact match; the 6 topics built afterward on its documented pattern (`area_perimeter`, `decimals`, `fractions_addition`, `lcm_hcf`, `measurement`, `multiplication_division`) all restricted candidate search to `_frontier()` — the immediate `.next` set — and rejected (or returned "no reachable next step") anything else. `fractions_addition/verifier.py` even carried an explicit comment defending this as deliberate, to stop a stray *grammar* match on a later step's shape from being silently accepted. Confirmed as a real bug: a student who jumps straight to the correct final answer, skipping intermediate steps the DAG still permits, was flagged wrong (and, downstream, the orchestrator's `problem_is_complete` check in `api/routes/sessions.py` never fires, so the problem never ends — the UI keeps demanding the skipped steps). Fixed by adding `Problem.reachable_step_ids()` (`schemas/step_schema.py`, a forward BFS closure over `.next` from the current frontier) and widening all 6 topics' candidate search to that reachable set: an exact match against the immediate frontier is still a clean accept (confidence 1.0); an exact match further along is accepted too but surfaced at `NON_ADJACENT_MATCH_CONFIDENCE` with `non_adjacent_valid_match`, identical to `subtraction_borrowing`'s existing tiering.

Three more-specific issues surfaced by exercising this against the real fixture set, fixed alongside it: (a) two reachable nodes can legitimately share the same expected value (e.g. a `simplify_fraction` step whose correct output equals the final answer) — `_resolve_exact_match`/`_resolve_near_match` now prefer a frontier match first, then an actually-terminal (`next == []`) match, before falling back to the first candidate found, so a value that both completes the problem and happens to satisfy an earlier node reads as "the student finished," and a near-miss reads as "wrong at the step the student is actually on," not an arbitrary pick between coincidentally-equal candidates (applied to `subtraction_borrowing` too, for consistency, though its whole-graph search made the risk latent there rather than exercised); (b) `fractions_addition`'s `write_final_answer` grammar (`free_text_parser.py::parse_final_answer`) always reduces to lowest terms by design (so "3/2" and "1 1/2" compare equal there) — under the widened search this let an *unsimplified* submission at an earlier step (e.g. "4/6" typed at `simplify_fraction`) silently reduce into a false "skipped to the end" match, masking exactly the "forgot to simplify" error the buggy-rule library exists to catch; fixed with a `reduce=False` literal-parse mode used only when evaluating `write_final_answer` as a non-frontier candidate, so a non-adjacent match still requires the *literal* submitted value to already equal the reduced final answer, not a value that only matches after reduction.

`_light_check`'s shared verifier was deliberately left alone: every light-check problem is 1-2 steps, so its frontier and reachable set already coincide — there's no further-along node to skip to.
**Why:** Reported directly (Bug 1/Bug 3 of a 4-bug batch): "student skips ahead, enters final answer early → flagged wrong instead of valid further-along path" and "Problem schema forces filling every predefined step even after early [completion]." The DAG-not-list schema (D11) and the non-adjacent-match confidence tier (D22) already had the right primitives for this — `subtraction_borrowing` proved the pattern works — the 6 newer topics just never inherited the full-reachability search, likely because each was built by mirroring the *previous* topic's file rather than the original's, and frontier-only search looks correct until specifically tested against a skip-ahead submission.
**Affects:** `schemas/step_schema.py` (`Problem.reachable_step_ids`), all 7 heavy topics' `verifier.py` (reachable-set search + frontier/terminal tie-breaking), `fractions_addition/free_text_parser.py` (`parse_final_answer(reduce=...)`). New regression tests: `tests/unit/verification/test_decimals_verifier.py`, `test_multiplication_division_verifier.py`, `test_fractions_addition_verifier.py` (direct-final-answer-from-the-start cases, terminal-node assertions). No change needed to `api/routes/sessions.py`'s `problem_is_complete` check or the frontend's `solved` detection (`ProblemSolver.tsx`) — both already derive correctly from `matched_step_id`/`next == []` once the verifier reports the right node.

### D72 — Confidence/agreement values rounded at construction to eliminate float-precision display noise (2026-08-23)

### D74 — Leakage filter's protected-field key list had silent gaps: several topics' real answer-output fields were never protected at all (2026-08-23)
**Decision:** While root-causing D73 live, the request log showed `'protected_values': []` for `area_perimeter`'s `compute_area` step — `_protected_values()`'s hardcoded key list (`result_digit`, `value`, `to_digit_after`, `num`, `den`, `left_num`/`left_den`/`right_num`/`right_den`, `op`, `answer`, `digits`) had never included `result` (area_perimeter's actual answer field for `compute_area`/`compute_perimeter`), meaning the leakage filter had zero protected values — and so could never reject anything — for that step type. Added a systemic regression test, `test_every_topics_answer_fields_are_protected`, that introspects every one of the 7 topics' actual Pydantic field models and fails if any `int`/`str`-typed field isn't explicitly classified as either protected or a known-safe visible input — a future topic's new answer field can no longer silently repeat this gap; it fails CI instead.

### D75 — Public `/problems/{id}` endpoint was leaking a step's answer directly through `given`, independent of any LLM path (2026-08-23)
**Decision:** Auditing every topic's `given` dict against its own `expected_state` shapes (prompted by D74's test) found `measurement`'s `given` includes `direction`/`factor` — which are the EXACT `expected_state` of that problem's own first step (`identify_conversion_factor`). `api/routes/problems.py::get_problem_public()` was passing `problem.given` straight through into `PublicProblem`, a response shape this same file's own docstring already says must never expose `expected_state` — but `given` itself was never checked for accidentally duplicating one. Every measurement problem shipped the answer to its own first step in this endpoint's plain JSON, readable from the browser's network tab before the student attempts anything, with zero LLM or dialogue-turn involvement — a strictly worse bug than a generated-message leak. Fixed with `_public_given()`: redacts a `given` key only when its value is IDENTICAL to that same key's value in one of the problem's own steps' `expected_state`, using `protected_fields.py`'s classification (D74) to decide which keys are candidates at all. Deliberately NOT a blanket "drop every key named in `PROTECTED_INT_KEYS`" — `given.value` (e.g. "3" in "3 km to m") is genuine, non-secret input under the same key name that means "the answer" inside `write_final_answer.value`; blanket redaction would have silently stripped real, needed input for every topic whose `given` happens to reuse a protected key name for legitimate input.
**Why:** Same non-negotiable-leakage-filter reasoning as D74, but for a structural leak the dialogue-message leakage filter can't touch at all — `contains_leakage()` only ever runs against LLM-generated text, never against the raw problem-catalog payload. Found via full-system audit ("test all the questions... improve the whole system"), not from a specific reported symptom — the founder never mentioned this one.
**Affects:** `api/routes/problems.py` (`_public_given()`, `PublicProblem.given` construction now calls it). New integration test `test_public_problem_endpoint_redacts_given_fields_that_duplicate_a_step_answer` (`tests/integration/test_api.py`) confirms both the redaction (`direction`/`factor` absent, `"1000"`/`"3000"` absent from the raw response body) and that `given.value` still comes through unredacted. Confirmed against real Postgres (integration test, not mocked).
