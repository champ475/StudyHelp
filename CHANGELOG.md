## 2026-08-14 10:00 — Phase 1: golden regression suite (30 cases), no threshold tuning needed

- `scripts/build_golden_cases.py`: generates the golden suite's JSON case files by pulling `expected_state` straight from the real seeded problem fixtures (via `load_problems()`), rather than hand-transcribing digits a second time — removes an entire class of "the test fixture disagrees with the real fixture" bugs. Not run automatically; a deliberate, reviewed-diff step when adding cases.
- `tests/golden/subtraction_borrowing/cases/*.json`: 30 generated cases across all 6 seeded problems, structured as `{case_id, problem_id, prior_accepted_steps, student_step, expected: {is_valid, matched_step_id, confidence_band, error_kind, error_note}}`. `confidence_band` (`accept`/`non_adjacent`/`reject`/`passthrough`/`structural`) rather than a bare float, so `ACCEPT_THRESHOLD`/`REJECT_THRESHOLD` can be retuned later without every case needing to encode the exact number. Breakdown: 9 accept, 4 non-adjacent, 9 reject (3 each for B1/B2/B3), 5 passthrough (4 ambiguous + B4), 3 structural rejection.
- `tests/golden/subtraction_borrowing/test_golden_regression.py`: single parametrized test loads each case, builds `ProblemState`, calls the real `verify_step()`, asserts against the expected band and exact verdict fields. All 30 cases + 2 coverage-sanity tests pass.
- **On threshold tuning, stated honestly:** the plan anticipated "expect iteration" here. In practice `ACCEPT_THRESHOLD=0.9` / `REJECT_THRESHOLD=0.75` / `NON_ADJACENT_MATCH_CONFIDENCE=0.85` (chosen in the previous commit) passed all 30 cases on the first run — no retuning was needed. Recorded as a real outcome, not claimed retroactively as "tuned."
- **A genuine, deliberately-kept finding: B4 (stale-borrow-digit) cannot land in the `reject` band under the Phase 1 field-agreement heuristic.** B1-B3 are single-field-divergent bugs (3 of 4 fields still match, agreement=0.75, right at the reject threshold). B4 is inherently two-field-correlated — using the stale pre-decrement digit changes both `minuend_digit` and the resulting `result_digit`, dropping agreement to 0.5, squarely in the `passthrough` band. This isn't a bug to fix in the verifier — it's the verifier correctly declining to confidently call something wrong when the evidence is genuinely ambiguous from a single step's field-comparison view (ARCHITECTURE.md D2's bias, working as designed). It's also the clearest concrete illustration yet of *why* Phase 2's buggy-rule matcher exists as a separate layer: it operates on the raw `(correct_step, student_step)` pair against a named pattern (already seeded, `subtraction_borrowing.stale_borrow_digit`), not a generic confidence threshold, so it can catch exactly this shape. `test_golden_suite_covers_all_four_buggy_rules` asserts this passthrough placement explicitly rather than papering over it.
- CI: added a dedicated `golden` job (matches `technical_architecture.md §11` step 2's explicit "regression tests passing before moving on" gate — a distinct, visible signal from the general `test` job).
